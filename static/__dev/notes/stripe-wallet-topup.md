# Stripe Wallet Top-up Flow Notes (Agent-Facing)

- **Completely Removed:** Apple Pay and Google Pay were completely removed from the codebase in 2026 by explicit user request. DO NOT re-add them (not even as fallback or optional) unless the user explicitly asks for it again.
- **Removed Code:** `components/WalletExpressCheckout`, `components/NativeWalletButton`, `helpers/nativeStripeWallet`, the wallet sections in `components/TopupPaymentDialog`, the Apple/Google Pay section in `components/AdminStripe` (including Stripe Payment Method Domains and related fields in `endpoints/admin/stripe/status_GET`), wallet translation keys (`topup.wallets_*`, `topup.wallet_native_*`, `topup.or_other`), the npm dependency `@capacitor-community/stripe`, as well as Apple/Google Pay doc files and plans.
- **Intentionally Kept:** The values `apple_pay` and `gpay` in the `paymentMethod` schema for `endpoints/wallet/create-payment-intent_POST` and `endpoints/wallet/confirm-topup_POST`, in the database enum, and in the label maps in `endpoints/cart/checkout_POST` and `endpoints/orders/modify_POST`. Do NOT clean these up, as historical data and older installed native app versions depend on them and must not break.
- **Current Top-up Methods:** Credit card, Klarna/Sofort, and Amazon Pay via Stripe PaymentElement (`components/TopupCardForm`), plus PayPal via the PayPal SDK. A PaymentIntent is only created once the user selects a payment method — there is no eager intent creation when opening the dialog.
- **Amazon Pay Integration:** Amazon Pay runs through the existing Stripe account (no separate Amazon Merchant contract needed), is already activated in the Stripe dashboard, and has been verified via PaymentIntent test. The value `amazon_pay` exists in the zod paymentMethodSchema (`endpoints/wallet/create-payment-intent_POST.schema.ts`), the DB enum `payment_method_type`, and the label maps in `endpoints/cart/checkout_POST` and `endpoints/orders/modify_POST`.
- **Amazon Pay Testing Note:** Amazon Pay is redirect-based and uses the same return flow as Klarna (`return_url` + `redirect: 'if_required'` in `components/TopupCardForm`, evaluating `payment_intent` / `topup_amount` / `topup_method` in `pages/account.tsx`). Because of this, testing is only possible in the published app, as the Floot sandbox iframe blocks redirects.
- **Background:** Apple Pay required the `com.apple.developer.in-app-payments` entitlement and a registered Merchant ID, which could not be directly configured via Floot. The required effort was disproportionate to the benefit.
- **Native App Redirect Flow:** Redirect payment methods (amazon_pay, klarna, klarna_sofort) do NOT run via the Stripe PaymentElement in the native app because the `return_url` in the local bundle points to `https://localhost`. Instead: `isNativeApp()` in `components/TopupPaymentDialog` switches to the external browser flow -> `endpoints/wallet/redirect-payment/start_POST` creates and confirms the PaymentIntent server-side via `payment_method_data` (Klarna with `billing_details` from the User Profile, Country DE) and returns `next_action.redirect_to_url.url`. The app opens this URL with `window.open(url, "_blank")` in the external browser. The `return_url` is hardcoded to `https://biberfieber.floot.app/zahlung-abgeschlossen` (Live domain, because the external browser cannot load the Sandbox domain). The public page `pages/zahlung-abgeschlossen` shows the result and provides a deep-link `com.silversurfer.biberfieber://` back into the app. The credit is not applied in the browser, but in the app: `helpers/useRedirectTopup` polls `endpoints/wallet/redirect-payment/status_POST` every 3s, which checks the PaymentIntent at Stripe (`metadata.userId` matching) and calls `creditWalletTopup`; "Payment already processed." is treated as already credited (idempotent). Web/PWA continue to use the unchanged PaymentElement flow in `TopupCardForm`. **Important:** The frontend is embedded in the local app bundle, so these changes will only take effect in the APK after a new native build; the root cause for this is described in `static/__dev/docs/native-app-updates-ohne-review.md` (Option A / Remote-Bundle would be the permanent solution).

## Reliability & Safety Nets

Due to previous incidents where redirect-based payments (like Amazon Pay) succeeded at Stripe but were not credited when the app failed to poll, several safety nets have been introduced:

1. **Public Webhook/Return Check:** The public return page (`pages/zahlung-abgeschlossen`) reads the `payment_intent` and aggressively calls `wallet/redirect-payment/complete_POST` to credit the user directly in the browser, independent of the native app polling.
2. **Scheduled Job (`reconcileTopups`):** A cron job runs every 15 minutes to automatically check the last 2 days of PaymentIntents for any successful, uncredited transactions and applies them.
3. **Admin Reconcile Tool:** An admin endpoint (`admin/stripe/reconcile-topups`) allows for manual, targeted reconciliation of specific intents or broader timeframe sweeps (defaults to `dryRun: true` to prevent accidental massive credits).
